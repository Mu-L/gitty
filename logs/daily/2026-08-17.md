## Why it matters

**Why do this?**

Three of the day's five commits are about controls sitting where the thing they
act on is not: a Send button in the file header that types into the terminal, a
filter strip above every log whether or not anything was being narrowed, a
long label on a button whose tooltip already explained it. The other two are
the missing keys — browsing the whole directory on disk was one item in a
context menu, a view you had to know was there.

**What problem does it solve?**

Moving Send to the terminal header keeps it on screen whatever the top-left
pane is showing. The filter behind a button gives the log its rows back and
makes "why is this list short?" answerable from what is on screen. Ctrl+B and
Ctrl+D make browsing a one-key trip in each direction, and each key brings its
layout with it, so switching view no longer means a second stop at the Panes
menu.

**What does it affect?**

The layout-with-a-view idea is now in `ref/spec/renderer.md`: `RepoTab` owns
the view, `App` owns pane visibility, and the tab asks through one
`onLayout(panes)` prop rather than reaching for `setPanes`. The chord functions
live in `panes.ts` beside the cycle chord with `test/panes.test.ts` pinning
them, and the terminal question — which keys a history browser gets to take
from a shell — is written down there rather than rediscovered per key.
