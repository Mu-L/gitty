## Why it matters

**Why do this?**

Pull is deliberately `--ff-only`, so it never rewrites history behind the user's
back. The cost of that choice is a dead end: the one case where a pull cannot
fast-forward is also the common case after committing locally, and the only
answer the app had was a refusal.

**What problem does it solve?**

It turns the dead end into a question. The user who wanted their commits replayed
on top says yes and gets it; the user who did not gets exactly the message they
got before. The narrowness matters as much as the offer — a rebase proposed after
a credential failure would be noise, so only the one recognisable divergence
triggers it.

**What does it affect?**

The pull path in `src/main/git.ts` and its handler, plus a native dialog whose
strings live in the main process's own message tables. The manual gains the
behaviour; `ref/spec/main-process.md` gains the reasoning, so the next person
reading the string match knows it is intentional rather than fragile.
